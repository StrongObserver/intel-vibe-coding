# 🧭 周末两天一夜 · 六人旅行决策工作台

> 把一段混乱的群聊，收敛成一份**能拍板、能执行、能发回群里**的周末旅行方案。
> 一个运行在本地、可实际操作的 Web App（纯 Python 标准库，零第三方依赖）。

---

## 一、如何运行

```bash
# 环境：任意 Python 3.6+（无需 pip install 任何东西）
python app.py
# 浏览器打开：http://127.0.0.1:8000
```

- 停止：`Ctrl+C`。
- 想保存你对需求的修改：用 `python app.py --save`，退出时会写入 `state.json`，
  下次启动自动读回（默认每次启动都从"群聊原始种子"开始，方便反复演示）。
- 可选端口：`PORT=8010 python app.py`。

### 运行测试（89 个用例）

```bash
python run_tests.py            # 全量
python run_tests.py t_planner  # 只看某模块（t_model/t_kb/t_conflicts/t_planner/t_export/t_api/t_e2e）
```

测试覆盖：模型校验、知识库完备性、冲突/不确定性、方案生成与硬约束、
决策导出、HTTP API 语义、以及"促导员真实使用旅程"的端到端联动。

## 二、核心设计思路：这不是"排行程工具"，而是"决策收敛工具"

群聊问题的本质不是信息太少，而是**信息混杂且互相拉扯**：
硬约束、偏好、事实、还没确定的事、各自的关注点挤在一起，谁说话都有道理，
于是**没人能拍板**。所以产品把"决策过程"拆成一条可操作的流水线：

1. **需求共识**：把群聊台词逐条翻译成结构化需求，区分
   硬约束（"必须/最快…才能/只能/我吃素"）/ 偏好（"最好/不想/比较想"），
   每条带**原文出处**和**我们为何这么判**，可随时翻转与改数值。
2. **冲突雷达 + 待确认清单**：先让"拉扯"显形——车坐不下、D 晚出发挤掉上午、
   A 的返程截止反向限制目的地、温泉 vs 预算、B 想拍自然但 C 不能走太多……
   同时把所有"还没定"的事（日期/天气/票/口径）变成**带负责人和时限的待办**。
3. **候选方案**：确定性引擎先定"两日骨架"（时间窗被硬约束框死，天然不排满），
   枚举 城市×交通×日块 → 硬约束过滤 → 软偏好逐人打分。产出多个候选，
   每个都标清楚**对谁、牺牲了什么**；若真的无解，明说卡在哪、松哪条可解。
4. **决策与导出**：逐人 接受/有保留/反对 → 生成一份**可直接发群聊的定稿**，
   含行程、费用口径、逐人核对、以及仍悬着的待确认项。

一句话：**让每个人看到自己的约束被尊重、自己的偏好被量化、牺牲被明示**，
方案才能被讨论与拍板。

## 三、用户真正需要解决的问题

表面是"帮忙排两天一夜的行程"，实际上是六个判断维度纠缠下的**群体决策问题**：

- **语义歧义**：同一句话里混着硬约束和偏好，语气词是线索（"必须"vs"最好"）。
- **约束互斥**：时间窗（11:00 出发 / 18:00 返沪）、交通容量（4 座车）、预算、
  体力上限彼此打架；一次只能满足一部分。
- **不确定性**：天气、票、日期、"800 含什么"都没定，方案必须能承载"预案"。
- **公平可见**：每人要能看出"这条没满足我"——否则没人愿意为集体让步。

因此产品价值不是"给出唯一正确行程"，而是**把决策所需的全部信息结构化、
让取舍可见可谈、最终落到一个可执行且可问责的计划**。

## 四、关键产品/技术决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | **Python 3 标准库 + 原生前端，零依赖** | 用户机器为 conda base，`python app.py` 即可跑，不给评委/使用者增加装环境成本 |
| 2 | **"两日骨架"式生成，而非背包求解器** | 硬约束把可用时间框死后，最佳实践是"每天 1 主项 + 至多 1 轻项"；确定性启发式可解释、可测试、可回滚 |
| 3 | **需求带 quote/note 可追溯 + 硬软可翻转** | 语义判断是核心观点，必须可审阅、可质疑，而不是黑盒 |
| 4 | **逐成员 gap（缺口）而非单一总评分** | 同一活动对不同人含义不同（博物馆：E 加分、B 减分）；总分数会掩盖"谁在牺牲" |
| 5 | **费用按"最贵成员口径"** | 混合交通里坐高铁的人实付更多，用均值会低估预算压力、误导 A |
| 6 | **雨天预案是"方案属性"而非附加页** | 天气是最大不确定项，把室内替身做成切换，避免临时抓瞎 |
| 7 | **硬约束由独立校验器 `validate_plan` 把关** | 生成器产出的每个方案都再过一遍校验，测试与 API 复用同一把尺，防未来改坏 |
| 8 | **数据"诚实粗算"**：价格/时间为估算、可编辑，知识库完备性有专门测试 | 服务决策讨论而非假装实时 OTA/时刻表精度 |
| 9 | **本地无状态默认启动**（可选 `--save`） | 演示可重复、测试可确定；持久化交给使用者按需开启 |

## 五、哪些需求没有实现，以及为什么

- **真实 OTA / 车票 / 天气 API 与实时比价** —— 题目要求"本地可运行"，外部依赖会破坏
  可离线、零安装；且决策问题不依赖绝对精度。
- **多人在线协同**（每人手机各自投票、实时同步）—— 产品面向"一台电脑 + 群里对着聊"
  的促导场景；真实协同需要账号/同步，会显著放大复杂度而偏离本题评价标准。
- **地图动线可视化 / 精确到分钟的时刻表** —— 属于锦上添花，与"决策收敛"主目标弱相关。
- **新增城市的精细知识库向导** —— 已允许用户自由编辑现有城市数据，
  但"任何新目的地都自动精准建模"需要开放地理数据源，不在本题范围。
- **更细粒度竞价/最优化的数学求解** —— 刻意选择可解释启发式：
  题目明言"不排满、不要太累"，最优解未必是最好方案。

## 六、当前方案的主要限制

- **知识库为人工策展估算**：价格/步行量/时段来自合理估计，会随真实情况变化；
  横向比较可靠，绝对数值需在使用前按实际核一遍（工具里已标注"估算"）。
- **活动池与时间模型简化**：把半天抽象成"1 个主项块"，对"两个点都很近、
  想拆成半小时+一小时"的行程不够精细；真遇到这种需求需扩展活动块粒度。
- **步行/开销估算粒度粗**：单日步数是"活动步数 + 基础转场步数"的累加，
  不含实时导航级精度。
- **单机单促导员**：不支持六人各自设备实时表态（见"未实现"）。
- **文本方案为主**：无地图、无日历文件（iCal）导出。
- **测试覆盖**：89 个用例覆盖模型/引擎/API/联动；前端交互通过 API 等价旅程与
  JS 语法检查验证，未做真实浏览器 UI 自动化（如 Playwright）。
